## Problem Statement

여행방 멤버가 방 진행 단계와 제출 시점에 맞는 설문을 제출할 API가 필요하다. 특히 첫 설문 마감 뒤 합류한 멤버의 응답은 받을 수 있어야 하지만, 마감 시각이 지난 응답이 이미 진행 중인 1차 설문 집계에 섞이면 안 된다. 동시 제출·합류·퇴장 상황에서도 방의 마감과 응답 상태가 일관되어야 한다.

## Solution

로그인한 활동 멤버가 `POST /api/rooms/{roomId}/survey`로 설문을 제출한다. 방 행 잠금 안에서 멤버와 제출 이력을 확인하고, 방 상태 및 마감 시각에 따라 검증·마감·안건 오픈·저장을 순서대로 처리한다. 마감 뒤 합류한 멤버의 첫 응답도 저장하되 1차 안건 집계에는 포함하지 않는다.

## User Stories

1. 여행방 멤버로서, 로그인 세션으로 설문을 제출하고 싶다. 그래야 제출한 응답이 내 방 멤버십에 연결된다.
2. 여행방 멤버로서, 활동 멤버일 때만 설문을 제출하고 싶다. 그래야 나간 멤버가 다시 방 데이터를 바꾸지 않는다.
3. 설문 작성자로서, 방이 없는 경우 명확한 `ROOM_NOT_FOUND` 응답을 받고 싶다. 그래야 잘못된 방 ID를 구분할 수 있다.
4. 설문 작성자로서, 방 멤버가 아니거나 방을 나간 상태라면 `FORBIDDEN` 응답을 받고 싶다. 그래야 접근 권한을 알 수 있다.
5. SURVEYING 단계의 멤버로서, 예산·숙박 유형·여행 페이스를 모두 입력하고 싶다. 그래야 1차 설문에서 세 안건의 기본 정보를 제공할 수 있다.
6. 설문 작성자로서, 허용된 범위 안의 예산만 제출하고 싶다. 그래야 예산이 1원 이상 99,999,999원 이하로 유지된다.
7. 설문 작성자로서, 유효한 숙박 유형과 여행 페이스만 제출하고 싶다. 그래야 서버가 지원하지 않는 값을 저장하지 않는다.
8. 설문 작성자로서, 선호 활동을 1~3개 중복 없이 선택하고 싶다. 그래야 응답을 일관되게 집계할 수 있다.
9. 설문 작성자로서, 기피 메모를 100자 이내로 작성하고 싶다. 그래야 알레르기나 피하고 싶은 활동을 전달할 수 있다.
10. PLANNING 또는 REVIEWING 단계의 멤버로서, 예산·숙박 유형·여행 페이스를 제출하지 못하게 하고 싶다. 그래야 이 단계에서 해당 항목이 설문으로 변경되지 않는다.
11. PLANNING 단계에 뒤늦게 합류한 멤버로서, 선호 활동과 기피 메모를 제출하고 싶다. 그래야 장소 선정과 후속 투표에서 내 취향도 고려된다.
12. REVIEWING 단계의 멤버로서, 설문 응답을 제출하고 싶다. 그래야 투표가 취소된 뒤 후보 장소 상세 정보에서 응답을 활용할 수 있다.
13. FINALIZED 방의 멤버로서, 설문 제출이 거절되길 원한다. 그래야 최종 확정된 계획이 설문으로 변경되지 않는다.
14. 1차 설문 마감 뒤 새로 합류한 멤버로서, 아직 응답 이력이 없다면 첫 설문을 제출하고 싶다. 그래야 `surveyClosedAt` 기록이 후발 멤버의 제출을 막지 않는다.
15.설문을 이미 제출한 멤버로서, 재제출이 `ALREADY_SUBMITTED`로 거절되길 원한다. 그래야 한 멤버의 응답이 중복 저장되지 않는다.
16. 마감 시각 전에 제출한 멤버로서, 내 응답이 저장된 뒤 1차 마감 조건을 평가받고 싶다. 그래야 마지막 응답이 1차 설문 집계에 포함된다.
17. 마감 시각 뒤 첫 제출을 하는 멤버로서, 제출은 성공하고 응답도 저장되길 원한다. 그래야 늦게 합류했더라도 의견을 남길 수 있다.
18. 마감 시각 뒤 아직 1차 마감 전인 방의 멤버로서, 기존 응답만으로 먼저 1차 설문을 마감하고 안건을 연 뒤 내 응답을 저장하고 싶다. 그래야 늦은 응답이 1차 안건 집계에 섞이지 않는다.
19. 1차 마감 후 제출하는 멤버로서, 응답만 저장되고 안건이 다시 열리지 않길 원한다. 그래야 후발 응답이 기존 안건 흐름을 되돌리지 않는다.
20.출발 전날 00:00 이후 설문 마감에 도달한 멤버로서, 마감은 기록되지만 새 안건은 열리지 않길 원한다. 그래야 투표할 수 없는 안건이 생성되지 않는다.
21. 방 멤버로서, 설문 제출과 합류·퇴장이 겹쳐도 한 번에 하나씩 처리되길 원한다. 그래야 활동 멤버 수와 응답 수를 기준으로 한 마감 판정이 안정적이다.
22. API 사용자로서, 성공 응답에서 설문 ID, 제출 시각, 이번 요청에서 1차 설문이 마감됐는지를 알고 싶다. 그래야 제출 결과와 방 진행을 화면에 반영할 수 있다.
23. API 사용자로서, 일반 제출은 201, 마감 시각 뒤 제출은 200으로 구분된 성공 응답을 받고 싶다. 그래야 늦은 제출도 오류가 아닌 성공으로 처리할 수 있다.

## Implementation Decisions

- 설문 도메인에 `POST /api/rooms/{roomId}/survey` 제출 API를 추가한다. 인증 사용자 ID는 controller에서 전달하며, service는 세션이나 SecurityContext를 직접 조회하지 않는다.
- 요청은 `budget`, `stayType`, `pace`, `actPrefs`, `avoidNote`로 구성한다. `budget` 범위는 1~99,999,999, `actPrefs`는 1~3개이고 중복 불가, `avoidNote`는 최대 100자다. 누락·잘못된 enum·잘못된 입력은 `INVALID_INPUT`; 활동 개수 오류는 `INVALID_ACTIVITY_COUNT`다.
- 방 상태에 따른 예산·숙박·페이스 규칙은 다음과 같다.
  - `SURVEYING`: 세 필드를 모두 필수로 검증한다.
  - `PLANNING`, `REVIEWING`: 세 필드를 요청에 포함하면 `INVALID_INPUT`으로 거부한다.
  - `FINALIZED`: `INVALID_STATUS`로 제출을 거부한다.
- avoidNote는 필수값이다. 누락되거나 공백만 있는 빈 값은 AVOID_NOTE_REQUIRED로 거부하고, 100자를 초과하면 AVOID_NOTE_TOO_LONG으로 거부한다.
- 서비스는 방 행 잠금을 먼저 잡고 방 존재 여부, 활동 멤버, 해당 멤버의 기존 응답 여부, 상태별 제출 규칙을 확인한다. 방 잠금으로 제출과 합류·퇴장·같은 방의 다른 직렬화 작업이 순서대로 처리된다.
- 이미 응답이 존재하는 멤버는 방 상태와 마감 시각에 관계없이 `409 ALREADY_SUBMITTED`다. DB의 `UNIQUE(plan_room_member_id)` 제약도 최종 방어선으로 유지하며, 예상된 unique 위반은 같은 오류 코드로 변환한다.
- `surveyClosedAt`은 1차 설문 마감을 기록하는 값이며 제출 가능 여부를 결정하지 않는다. 마감 뒤 합류한 미제출 활동 멤버는 첫 설문을 제출할 수 있다.
- 마감 시각 전 `SURVEYING` 제출은 응답을 저장한 뒤 5-1 조건을 확인한다. 마지막 제출까지 포함해 마감 조건을 만족하면 설문을 마감하고 1차 안건 오픈을 시도한다.
- 마감 시각 이후의 첫 제출도 성공시킨다. `surveyClosedAt == null`이면 기존 응답 집계로 먼저 설문을 마감하고 1차 안건 오픈을 시도한 후 새 응답을 저장한다. 이 늦은 응답은 1차 안건 집계에 포함하지 않는다. `surveyClosedAt != null`이면 응답만 저장하며 안건을 다시 열지 않는다.
- 출발 전날 00:00 이후에는 설문 마감 시각을 기록하되 안건을 오픈하지 않는다.
- 5-1 마감은 방 상태를 바꾸지 않는다. 기존 안건 판정 흐름이 모든 설문 안건의 마감을 확인한 뒤 `PLANNING`으로 전환한다.
- 현재 코드에서 기존 설문 응답 집계를 사용해 1차 안건을 여는 메서드를 찾지 못했다. 해당 메서드가 구현 시에도 없다면 오픈 연결 지점에 TODO를 남기며, 별도 안건 집계 알고리즘은 이 티켓에서 새로 설계하지 않는다.
- `REVIEWING` 응답은 저장만 하며, 투표를 취소하거나 방 상태를 변경하지 않는다. 투표 취소 뒤 응답이 후보 장소 상세 정보에서 활용되는 흐름은 이 API의 책임이 아니다.
- 성공은 공통 `ApiResponse` envelope와 `SURVEY_SUBMITTED` code를 사용한다. 마감 전 및 이미 1차 마감된 상태의 일반 성공은 HTTP 201, 마감 시각 뒤의 성공은 HTTP 200이다. 응답 데이터는 `surveyId`, 한국 시간 기준 오프셋 없는 `submittedAt`, 이번 요청이 1차 설문을 마감했으면 `surveyClosed: true`, 아니면 `false`를 담는다.
- 에러 계약: 로그인/세션 만료 401 `UNAUTHORIZED`; 숫자가 아닌 `roomId`와 잘못된 요청 400 `INVALID_INPUT`; 없는 방 404 `ROOM_NOT_FOUND`; 비멤버·퇴장 멤버 403 `FORBIDDEN`; 재제출 409 `ALREADY_SUBMITTED`; `FINALIZED` 제출 409 `INVALID_STATUS`.
- 요청 및 응답 시각은 `LocalDateTime`으로 표현하고 주입된 `Clock`을 사용한다.
- 저장소 스키마는 응답 행, 선택적 단계별 값, 유니크 멤버 제약을 이미 지원하므로 별도 마이그레이션은 추가하지 않는다.
- 성공적인 제출·마감의 방 활동 기록이나 SSE 이벤트 추가는 이 명세에서 요구되지 않으므로 범위에 포함하지 않는다.

## Testing Decisions

- 좋은 테스트는 내부 메서드 호출 횟수나 구현 구조가 아니라 외부 HTTP 응답, 영속된 응답과 방 상태, 마감 후 안건 집계에 드러나는 동작을 검증한다.
- 주 테스트 경계는 실제 로그인 세션과 Testcontainers MySQL을 이용한 설문 제출 HTTP 통합 테스트다. 정상 응답, 오류 상태와 code, 응답 본문, DB 저장 결과를 확인한다.
- 검증 사례에는 인증 실패, 잘못된 `roomId`, 방 없음, 비멤버·퇴장 멤버, SURVEYING 필수값과 범위, 잘못된 enum, 활동 개수 0·4개·중복, 기피 메모 길이, 단계에 금지된 예산·숙박·페이스, 재제출, FINALIZED, REVIEWING 및 PLANNING 저장을 포함한다.
- 마감 경계 테스트는 마감 전 마지막 응답이 1차 집계에 포함되는지, 마감 시각 후 제출이 HTTP 200으로 저장되면서 기존 응답으로 먼저 마감·안건 오픈되는지, 이미 마감된 뒤 제출은 안건을 재오픈하지 않는지, 출발 전날 이후 안건을 열지 않는지 확인한다.
- 동시성 테스트는 방 잠금 동작을 실제 DB로 검증한다. 마지막 두 제출, 제출과 합류, 제출과 퇴장이 겹칠 때 중복 저장이 없고 마감 처리가 한 번만 발생하는지 확인한다.
- 도메인 규칙 단위 테스트는 기존 `SurveyResponseTest` 경계를 재사용해 필수값, 범위, 메모 및 활동 선호 검증을 확인한다. HTTP 계약과 DB 동시성은 통합 테스트가 담당한다.
- 테스트 선례는 인증 포함 HTTP API 통합 테스트, Testcontainers MySQL, 방 잠금 통합 테스트, 설문 응답 엔티티 단위 테스트다.

## Out of Scope

- 설문 응답 수정 및 삭제 API
- 프론트엔드 설문 UI
- 1차 설문 응답을 집계해 안건 선택지를 만드는 세부 정책 및 새로운 안건 생성 알고리즘
- 투표 취소와 후보 장소 상세 정보의 설문 데이터 사용
- 설문 제출용 알림, SSE 이벤트 또는 방 활동 내역 이벤트 추가
- 설문 응답 테이블 스키마 변경

## Further Notes

- `surveyClosedAt`은 최초 설문 마감을 기록하며, 후발 멤버의 첫 설문 제출은 그 뒤에도 가능하다.
- 활동 멤버 정의는 기존 용어집을 따른다. 활동 멤버는 합류했고 아직 방을 나가지 않은 멤버다.
- 설문 옵션 API의 기존 enum과 한도 정의를 재사용한다.
