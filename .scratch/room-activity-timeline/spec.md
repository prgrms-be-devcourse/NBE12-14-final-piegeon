## Problem Statement

방 멤버는 여러 도메인에서 일어나는 중요한 변경을 시간순으로 한 화면에서 확인하고 싶다. 공통 방 활동 내역 저장 구조는 있지만, 이를 타임라인으로 조회하고 SSE로 실시간 전달하는 연결 구조가 없어 화면에서 새 활동을 누락 없이 표시할 수 없다.

## Solution

방 활동 내역을 타임라인과 SSE의 공통 데이터 원천으로 사용한다. 방 화면은 방별 SSE 연결 하나를 열고, 연결 준비 기준 ID를 받은 뒤 최신순 타임라인 조회와 실시간 수신분을 ID로 합친다. 모든 도메인은 공통 발행·구독 계약을 통해 커밋된 방 활동을 전달한다. 타임라인은 최신순으로 누적하고, 페이지 조회·재연결·읽음 처리·멤버 권한을 동일한 방 활동 내역 ID 계약으로 관리한다.

## User Stories

1. 방 멤버로서, 방에서 일어난 주요 업무 행위를 최신순 타임라인으로 보고 싶다. 그래야 다른 멤버와 시스템의 진행 상황을 파악할 수 있다.
2. 방 멤버로서, 서로 다른 도메인에서 발생한 활동을 한 타임라인에서 보고 싶다. 그래야 도메인별 화면을 오가며 변경을 찾지 않아도 된다.
3. 방 멤버로서, 새 활동이 SSE로 실시간 반영되길 원한다. 그래야 방을 새로고침하지 않고도 진행 상황을 볼 수 있다.
4. 방 멤버로서, 한 업무 행위가 타임라인 항목 하나로 보이길 원한다. 그래야 내부 데이터 변경 수와 관계없이 업무 흐름을 이해할 수 있다.
5. 방 멤버로서, 기록 당시의 요약 문구를 보고 싶다. 그래야 대상이 나중에 수정되거나 삭제되어도 당시 변경을 이해할 수 있다.
6. 방 멤버로서, 각 활동의 행위자, 대상 종류, 대상 ID, 행위 종류를 확인하고 싶다. 그래야 누가 무엇을 어떻게 바꿨는지 알 수 있다.
7. 방 멤버로서, 멤버가 일으킨 활동은 현재 멤버 이름으로, 자동 처리는 시스템 행위로 표시되길 원한다. 그래야 활동의 출처를 구분할 수 있다.
8. 방 멤버로서, 설문 마감·조율 완료·안건 결정·장소 단계 변경·일정 변경·최종 확정처럼 중요한 활동을 보고 싶다. 그래야 방 계획에 영향이 있는 변경을 파악할 수 있다.
9. 방 멤버로서, 개별 표·동의와 코멘트는 타임라인에 쌓이지 않길 원한다. 그래야 중요한 활동을 지나치게 자주 발생하는 변경 속에서 놓치지 않는다.
10. 방 멤버로서, 장소 후보의 동의 수 변경은 보지 않고 실제 단계 변경만 보고 싶다. 그래야 후보의 의미 있는 상태 변화에 집중할 수 있다.
11. 방 멤버로서, 시스템이 설문을 마감하거나 자동 처리한 행위도 타임라인에서 보고 싶다. 그래야 시스템에 의해 발생한 변경도 알 수 있다.
12. 방 멤버로서, 활동을 최신 항목부터 페이지 단위로 읽고 싶다. 그래야 이전 기록을 필요할 때 이어서 확인할 수 있다.
13. 방 멤버로서, 이전 페이지를 불러와도 이미 본 활동이 중복되지 않고 빠진 기록도 없길 원한다. 그래야 타임라인을 일관되게 읽을 수 있다.
14. 방 멤버로서, 방 화면에 들어갈 때 해당 방의 SSE 연결 하나를 사용하고 싶다. 그래야 방별 권한과 커서를 명확하게 유지할 수 있다.
15. 방 멤버로서, 첫 화면을 불러오는 사이 발생한 활동을 놓치지 않길 원한다. 그래야 초기 조회와 실시간 구독 사이에 공백이 없어야 한다.
16. 방 멤버로서, 첫 연결 뒤 조회한 타임라인과 연결 중 수신한 활동이 ID 기준으로 합쳐지길 원한다. 그래야 경계 시점의 중복을 제거하고 누락을 막을 수 있다.
17. 방 멤버로서, 연결이 끊겼다가 돌아오면 마지막 수신 ID 뒤의 영속 활동을 순서대로 다시 받고 싶다. 그래야 잠시 오프라인이어도 타임라인을 복구할 수 있다.
18. 방 멤버로서, 재연결 누락이 200건을 넘으면 재동기화 안내를 받고 필요한 화면 데이터를 다시 조회하고 싶다. 그래야 일부만 받은 불완전한 기록을 전체 기록으로 오해하지 않는다.
19. 방 멤버로서, 재연결 시 ID가 없는 일시 이벤트는 다시 받지 않길 원한다. 그래야 영속 기록과 순간 상태 변경을 혼동하지 않는다.
20. 방 멤버로서, 읽고 있던 이전 항목의 위치가 실시간 활동 때문에 이동하지 않길 원한다. 그래야 새 활동을 표시하면서도 읽던 내용을 이어갈 수 있다.
21. 방 멤버로서, 최신 항목을 보고 있을 때 새 활동이 타임라인 맨 위에 추가되길 원한다. 그래야 가장 최근 상황을 바로 확인할 수 있다.
22. 방 멤버로서, 이전 항목을 읽는 동안 새 활동이 있음을 별도 표시로 알길 원한다. 그래야 읽던 위치를 잃지 않고 새 항목으로 이동할 수 있다.
23. 방 멤버로서, 활동 대상이 남아 있으면 해당 화면으로 이동하고 싶다. 그래야 활동의 상세 맥락을 바로 확인할 수 있다.
24. 방 멤버로서, 대상이 삭제되었거나 이동할 수 없는 활동도 기록 문구로 읽을 수 있길 원한다. 그래야 과거 변경의 맥락이 유지된다.
25. 방 멤버로서, 타임라인에 실제 표시된 활동까지만 읽음 처리되길 원한다. 그래야 아직 보지 않은 활동이 읽음 처리되지 않는다.
26. 방 멤버로서, 확인 시각이 더 오래된 값으로 되돌아가지 않길 원한다. 그래야 읽음 상태가 안정적으로 유지된다.
27. 방을 나간 사용자로서, 열려 있는 해당 방 SSE 연결이 종료되길 원한다. 그래야 더 이상 참여하지 않는 방의 활동을 받지 않는다.
28. 방을 나간 사용자로서, 재접속으로 해당 방 활동을 받을 수 없길 원한다. 그래야 방 활동은 활동 멤버만 접근할 수 있다.
29. 로그인하지 않은 사용자로서, 타임라인과 SSE 활동을 읽을 수 없길 원한다. 그래야 방 활동이 인증된 사용자에게만 공개된다.
30. 활동 멤버로서, 방을 영구 삭제하면 방이 소유한 활동 기록도 함께 정리되길 원한다. 그래야 고아 기록이 남지 않는다.
31. 도메인 개발자로서, 공통 기록 서비스와 발행·구독 계약을 사용해 활동을 남기고 싶다. 그래야 새 도메인도 같은 규칙으로 타임라인과 SSE에 참여할 수 있다.
32. 도메인 개발자로서, 상태 변경과 활동 기록이 한 트랜잭션으로 처리되길 원한다. 그래야 실패한 변경이 타임라인에 노출되지 않는다.
33. 도메인 개발자로서, 공통 활동은 트랜잭션 커밋 후에만 실시간 발행되길 원한다. 그래야 롤백된 변경을 구독자가 받지 않는다.
34. 도메인 개발자로서, 여러 도메인의 활동이 같은 방에서 안전한 ID 순서로 재생되길 원한다. 그래야 동시 변경 뒤에도 재연결에서 활동을 놓치지 않는다.
35. 방 멤버로서, 다른 방의 활동이 내 타임라인이나 재연결 결과에 섞이지 않길 원한다. 그래야 방 경계를 유지할 수 있다.
36. 특정 사용자로서, 방 멤버가 공유하는 활동과 나에게만 전달되는 개인 알림이 구분되길 원한다. 그래야 서로 다른 전달 목적을 혼동하지 않는다.

## Implementation Decisions

- 기존 방 활동 내역을 타임라인·비접속 요약·SSE 재연결의 공통 영속 데이터 원천으로 재사용한다. 이를 감사 로그나 전체 이벤트 소싱으로 확장하지 않는다.
- 방 활동 타임라인은 활동이 최신순으로 누적되는 화면이며, 개인 알림은 별도 개념이다.
- 각 도메인은 업무 상태 변경과 같은 트랜잭션에서 공통 기록 서비스를 사용한다. 업무 행위당 한 기록을 저장하고 기록의 방, 선택적 행위자, 대상 종류·ID, 이벤트 종류, 행위 상태, 당시 요약을 보존한다.
- 공통 발행·구독 계약으로 기록을 전달하고 실제 SSE 발행은 트랜잭션 커밋 후 수행한다. 전송 직전 서버가 종료되어 빠진 실시간 전달은 재접속 재생으로 복구한다.
- 방별 기록은 방 잠금으로 직렬화하며 로그 ID를 타임라인 페이지 커서와 SSE 재연결 커서로 사용한다.
- SSE는 방 화면마다 방별 연결 하나를 사용한다. 연결 준비 시 서버가 구독을 등록한 뒤 현재 마지막 활동 ID를 기준점으로 준비 이벤트를 보낸다.
- 클라이언트는 연결 준비 기준 ID를 받은 뒤 일반 최신순 커서 페이지를 조회한다. 초기 조회가 끝날 때까지 수신한 SSE 이벤트를 버퍼링하고 조회 결과와 ID 기준으로 합쳐 중복을 제거한다. 조회 API에는 상한 ID(`throughId`) 파라미터를 두지 않는다.
- 타임라인 조회는 최신 ID 내림차순이며 페이지 크기는 1~100, 기본 20이다. 다음 페이지는 현재 가장 오래된 활동 ID보다 작은 ID를 커서로 사용한다.
- `activity` 실시간 이벤트만 저장된 활동 기록과 같은 항목 데이터를 사용하고 해당 `change_log` ID를 SSE ID로 사용한다. `agenda.resolved`, `vote.updated` 등 도메인 이벤트와 제어 이벤트는 SSE ID를 설정하지 않는다.
- 재연결은 Last-Event-ID가 가리키는 `change_log` ID보다 큰 영속 활동 기록만 ID 오름차순으로 재생한다. 도메인 이벤트는 영속 기록이 아니므로 재생하지 않는다. 누락이 200건을 초과하면 일부 재생 대신 `resync.required`를 보내고 클라이언트는 관련 방 화면 데이터를 재조회한다.
- `resync.required`는 SSE ID가 없는 제어 이벤트다. 클라이언트는 기존 연결을 닫고 관련 화면 데이터를 다시 조회한 뒤 새 연결을 연다.
- 표·동의·코멘트 등 ID가 없는 일시적 도메인 이벤트는 영속 기록에 저장하지 않으며 재연결 시 재전송하지 않는다.
- 최신 위치에 있는 사용자는 새 활동을 타임라인 맨 위에서 바로 보고, 이전 기록을 읽는 사용자는 현재 위치를 유지하면서 새 활동 표시를 본다.
- 타임라인 활동은 대상 종류와 ID를 제공한다. 대상이 존재하면 해당 화면으로 이동하고, 삭제 또는 이동 불가 상태면 기록 문구를 표시한다.
- 읽음 처리는 화면에 실제 표시된 활동까지만 한다. 확인 API의 기존 계약대로 마지막으로 표시한 활동의 `createdAt`을 `LocalDateTime` `seenUntil`로 전달하고, 저장된 마지막 확인 시각보다 과거 값으로 되돌리지 않는다.
- 방 활동과 타임라인은 활동 멤버만 읽을 수 있다. 방 멤버가 나가면 활성 SSE 연결을 종료하고 재접속도 거부한다.
- SSE 연결은 15초 주기의 keep-alive에서 활동 멤버 자격을 다시 확인한다. 방을 나간 멤버의 스트림은 다음 확인에서 종료하고 재접속은 즉시 거부한다.
- 이번 연결 관리 범위는 단일 서버다. 다중 서버 간 실시간 전달은 배포 요구가 생길 때 공유 발행기로 확장한다.
- 이 구현은 공통 `changelog`와 `room`, `room member`, `survey` 경계에 한정한다. 장소·안건·일정 도메인은 수정하거나 활동 생산자로 연결하지 않는다.
- 타임라인은 `GET /api/rooms/{roomId}/change-logs`에서 `cursor`, `size`로 조회하며, `cursor`보다 작은 ID를 최신순으로 반환한다. `size` 기본값은 20, 범위는 1~100이다. 응답 항목은 `logId`, 선택적 `actor`(`memberId`, `name`), `entityType`, `entityId`, `action`, `summary`, `createdAt`을 포함한다. 시스템 행위는 `actor: null`이다. 더 없으면 `nextCursor`는 `null`이다.
- SSE는 `GET /api/rooms/{roomId}/events`에서 연결한다. `connected` 이벤트는 `latestEventId` 기준점을 보내고, `activity`는 영속 활동 ID를 SSE ID로 사용한다. Last-Event-ID 누락이 200건을 넘으면 `resync.required`를 보낸다.
- 사용자별 동시 SSE 연결은 최대 3개다. 초과 시 HTTP 429 `TOO_MANY_STREAMS`를 반환한다.
- 방 멤버 조회는 방이 없으면 `ROOM_NOT_FOUND`, 비멤버와 나간 멤버는 구분 없이 `FORBIDDEN`을 반환한다.
- 확인 API는 `POST /api/rooms/{roomId}/seen`이며, 마지막으로 표시한 활동의 `createdAt`을 `LocalDateTime` `seenUntil`로 받는다.
- 기존 방 멤버의 활동 권한, 활동 종류와 요약 기준, 200건 재연결 한도, 데이터베이스 스키마와 시간 정책은 방 활동 내역 명세 및 ADR의 결정을 따른다.
- 구현 대상은 백엔드 공통 활동 조회·발행·SSE 및 읽음 API 계약이다. 저장소에 프론트엔드 구현체가 없어 이 명세는 화면 동작 계약을 정의하되 프론트엔드 코드 변경은 포함하지 않는다.

## Testing Decisions

- 좋은 테스트는 내부 호출 순서나 특정 SSE 구현 클래스를 검증하기보다 실제 인증 HTTP 요청과 연결에서 관찰되는 응답, 이벤트 ID·순서·권한·재연결 결과를 확인한다.
- 하나의 인증 포함 `ChangeLogTimelineIntegrationTest` 통합 경계를 사용한다. 실제 HTTP와 Testcontainers MySQL로 활동 기록, 타임라인 페이지, SSE 준비 기준점과 실시간 전달, Last-Event-ID 재생 및 재동기화, 권한 종료, 확인 시각 단조 증가를 검증한다.
- 통합 시나리오는 도메인 상태 변경을 수행해 활동이 커밋 전에는 보이지 않고 커밋 후에만 전달되는지 확인한다. 재연결에서는 다른 방 활동 혼입, ID 순서와 200건 초과 처리를 확인한다.
- 타임라인 초기 로딩 테스트는 상한 ID 없는 최신순 조회 결과와 연결 중 수신 이벤트를 ID로 합칠 때 중복을 제거하고 활동을 누락하지 않는지 확인한다.
- 테스트 선례는 인증을 포함해 실제 HTTP 흐름을 확인하는 `AuthIntegrationTest`, 방 API의 HTTP 권한·응답을 확인하는 `RoomReadApiIntegrationTest`, MySQL 저장 경계를 검증하는 `ChangeLogRepositoryTest`다.
- UI 위치 보존과 새 활동 표시 동작은 백엔드 저장소에 프론트엔드 테스트 하네스가 없으므로 이 명세의 화면 계약으로 정의한다.

## Out of Scope

- 방 공통 활동과 다른 개인 알림 기능.
- 다중 서버 간 실시간 브로커·공유 발행 구조.
- 기존 범위를 넘어서는 감사 목적 DB 변경 이력이나 이벤트 소싱.
- 개별 투표·동의·코멘트의 영속 활동 기록과 재연결 재생.
- 설문·안건·장소·일정 각 도메인의 업무 상태 전이 변경.
- 프론트엔드 화면 코드와 프론트엔드 테스트 하네스 추가.
- 장소·안건·일정 도메인의 활동 기록 연결.
- 기존 비접속 요약의 그룹 분류와 문구 정책 변경.

## Further Notes

- 용어는 `방 활동 내역`, `방 활동 타임라인`, `활동 멤버`, `개인 알림`을 사용한다.
- 기존 방 활동 내역 저장 구조와 도메인 기록 연결 일부는 이미 존재한다. 이 명세의 목적은 공통 발행·구독 계약과 방 화면에서 사용하는 타임라인·SSE 소비 계약을 완성하는 것이다.
- API 성공 응답은 기존 `ApiResponse` 규칙을 따른다. SSE 연결은 서버 이벤트 스트림 응답을 사용한다.
