## Problem Statement

여행 설문 화면은 숙소 유형, 여행 속도, 선호 활동 선택지를 표시해야 하지만, 이 목록을 프론트엔드에서 별도로 관리하면 서버의 설문 enum과 표시값이 달라질 수 있다. 예산은 선택지가 아니라 직접 입력하는 값이므로 입력 가능한 범위만 필요하다.

## Solution

로그인한 사용자에게 방과 무관한 정적 설문 선택지와 입력 한도를 제공하는 `GET /api/survey-options`를 구현한다. 응답은 서버의 숙소 유형, 여행 속도, 활동 코드 enum을 사용해 구성하고 `ApiResponse` 형식으로 반환한다.

## User Stories

1. 여행 설문을 작성하는 사용자로서, 숙소 유형 선택지를 서버에서 받고 싶다. 그래야 화면의 선택지가 서버가 허용하는 값과 일치한다.
2. 여행 설문을 작성하는 사용자로서, 각 숙소 유형의 기계용 값과 한국어 표시 라벨을 함께 받고 싶다. 그래야 선택값을 제출하면서 읽기 쉬운 문구를 표시할 수 있다.
3. 여행 설문을 작성하는 사용자로서, 여행 속도 선택지를 서버에서 받고 싶다. 그래야 여유로운 일정부터 바쁜 일정까지 지원되는 선택을 표시할 수 있다.
4. 여행 설문을 작성하는 사용자로서, 활동 선호 선택지를 서버에서 받고 싶다. 그래야 음식, 자연, 액티비티, 쇼핑, 문화 선호를 일관된 코드로 제출할 수 있다.
5. 여행 설문을 작성하는 사용자로서, 선택지 배열이 서버 enum 선언 순서로 오길 원한다. 그래야 화면에서 합의된 순서를 그대로 표시할 수 있다.
6. 여행 설문을 작성하는 사용자로서, 예산의 최솟값과 최댓값을 받고 싶다. 그래야 선택지를 만들지 않고 직접 입력하는 예산을 검증할 수 있다.
7. 여행 설문을 작성하는 사용자로서, 선택할 수 있는 활동 선호 개수의 최솟값과 최댓값을 받고 싶다. 그래야 선택 개수를 사용자에게 안내하고 검증할 수 있다.
8. 여행 설문을 작성하는 사용자로서, 회피 메모의 최대 길이를 받고 싶다. 그래야 입력 UI와 검증을 서버 계약에 맞출 수 있다.
9. 로그인한 사용자로서, 이 정적 데이터를 방 ID 없이 조회하고 싶다. 그래야 설문 작성 전에 특정 여행방에 종속되지 않고 선택지를 불러올 수 있다.
10. 로그인하지 않았거나 세션이 만료된 사용자로서, 선택지 조회가 `401 UNAUTHORIZED`로 거부되길 원한다. 그래야 인증이 필요한 API 정책이 일관된다.
11. 프론트엔드 개발자로서, 성공 여부와 성공 코드가 포함된 공통 API 응답을 받고 싶다. 그래야 기존 응답 처리 흐름을 재사용할 수 있다.
12. 프론트엔드 개발자로서, 응답 값이 바뀌었는지 확인하기 위해 배포된 API에서 선택지와 한도를 한 번에 받고 싶다. 그래야 화면에 여러 개의 정적 복사본을 유지하지 않아도 된다.

## Implementation Decisions

- 설문 도메인에 방과 무관한 조회 API를 추가하며 DB 스키마 변경은 하지 않는다.
- `GET /api/survey-options`는 로그인 세션을 요구한다. 미인증 또는 만료된 세션은 HTTP 401, code `UNAUTHORIZED`로 응답한다.
- 성공 응답은 HTTP 200이며 `ApiResponse` envelope의 `success`는 `true`, `code`는 `SURVEY_OPTIONS_FETCHED`다. `data`에 선택지와 한도를 담는다.
- `data.stayTypes`, `data.paces`, `data.actPrefs`의 각 항목은 `value`, `label` 필드를 가진다. `value`는 enum 상수명이고 `label`은 해당 enum의 표시 라벨이다.
- 각 선택지 목록의 순서는 기존 `StayType`, `Pace`, `ActivityCode` enum 선언 순서를 따른다. 값과 라벨은 기존 enum 정의를 사용한다.
- `data.limits`는 `budgetMin=1`, `budgetMax=99,999,999`, `actPrefsMin=1`, `actPrefsMax=3`, `avoidNoteMaxLength=100`을 제공한다. 예산은 선택지 목록이 아니라 직접 입력 범위로 제공한다.
- 성공 code는 프로젝트 API 규칙의 대상-결과 형식인 `SURVEY_OPTIONS_FETCHED`를 사용한다.
- 선택지 API는 어떤 방의 존재나 멤버십에도 의존하지 않으며 조회 시 상태를 변경하지 않는다.
- 읽기 쉬운 용어집 정의를 추가할 정도의 새 도메인 개념은 없고, 선택지 조회는 되돌리기 쉬운 계약이므로 ADR은 추가하지 않는다.

## Testing Decisions

- 좋은 테스트는 내부 구현 호출이나 enum을 읽는 구체적 방식을 검증하는 대신 실제 HTTP에서 확인되는 상태 코드, 공통 응답 구조, 선택지 값·라벨·순서, 입력 한도를 검증한다.
- 인증을 포함한 단일 HTTP 통합 테스트 경계를 사용한다. 로그인한 요청의 전체 응답과 비로그인 요청의 401 응답을 확인한다.
- 로그인 응답은 각 enum 목록의 항목과 순서, 한도값, HTTP 200, `SURVEY_OPTIONS_FETCHED`를 검증한다. 비로그인 응답은 HTTP 401과 `UNAUTHORIZED`를 검증한다.
- 기존 `IntegrationTest`의 실제 서버/Testcontainers 구성과 인증 포함 HTTP API 통합 테스트 선례를 따른다.
- DB 상태 변경이 없어 마이그레이션이나 DB 검증은 필요하지 않다.

## Out of Scope

- 설문 응답 제출·수정·삭제 API
- 예산을 고정 선택지로 제공하는 기능
- 설문 화면 및 프론트엔드 입력 검증 구현
- 선택지의 사용자별·방별 커스터마이징
- DB 스키마 변경 또는 마이그레이션

## Further Notes

- 현재 숙소 유형, 여행 속도, 활동 코드 enum의 값과 라벨은 명세에 제시된 목록과 일치한다.
- API는 정적 데이터이지만 명세상 로그인 세션이 필요하다.
