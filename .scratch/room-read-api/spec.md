## Problem Statement

사용자는 자신이 참여 중인 여행방을 다시 찾고, 방의 현재 정보와 멤버별 설문 진행 상황을 확인해야 한다. 현재 방 생성 외에 내 방 목록과 방 상세를 조회하는 API 계약이 없어, 프론트엔드가 방 진입 화면과 상세 화면을 구성할 수 없다.

## Solution

인증된 사용자에게 내 방 목록을 제공하는 `GET /api/rooms`와 방 상세를 제공하는 `GET /api/rooms/{roomId}`를 구현한다. 내 방은 사용자가 활동 멤버로 남아 있는 모든 방이며, 방 상태와 여행 날짜에 관계없이 포함한다. 목록은 한 번의 집계 쿼리로 조회하고, 상세는 방 정보와 멤버 목록을 일괄 조회해 멤버별 N+1을 피한다.

## User Stories

1. 여행 멤버로서, 내가 활동 멤버로 남아 있는 방 목록을 보고 싶다. 그래야 진행 중인 여행 계획으로 다시 들어갈 수 있다.
2. 여행 멤버로서, 내가 나간 방은 내 방 목록에서 제외되길 원한다. 그래야 현재 참여하지 않는 방과 혼동하지 않는다.
3. 여행 멤버로서, 최종 확정된 방과 여행 날짜가 지난 방도 나가기 전까지 목록에서 확인하고 싶다. 그래야 확정된 계획을 다시 볼 수 있다.
4. 여행 멤버로서, 출발일이 가까운 순으로 방을 보고 싶다. 그래야 가까운 여행을 먼저 찾을 수 있다.
5. 여행 멤버로서, 출발일이 같은 방은 방 ID 순으로 일관되게 보고 싶다. 그래야 목록의 순서가 안정적이다.
6. 여행 멤버로서, 내 방 목록에서 방 이름, 목적지, 여행 기간, 상태와 의견 마감 시각을 확인하고 싶다. 그래야 방을 열기 전에 어떤 여행인지 알 수 있다.
7. 여행 멤버로서, 각 방의 활동 멤버 수를 확인하고 싶다. 그래야 현재 참여 인원을 알 수 있다.
8. 여행 멤버로서, 내 설문 제출 여부를 목록에서 확인하고 싶다. 그래야 미제출 설문이 있는 방을 찾을 수 있다.
9. 여행 멤버로서, 참여 중인 방이 없으면 빈 목록을 받고 싶다. 그래야 빈 상태 화면을 표시할 수 있다.
10. 여행 멤버로서, 페이지네이션 없이 내 방 전체를 한 번에 받고 싶다. 그래야 현재 정해진 목록 계약을 단순하게 사용할 수 있다.
11. 활동 멤버로서, 방 이름·목적지·여행 기간·초대 코드·상태와 주요 시각을 상세 조회하고 싶다. 그래야 방의 계획 정보를 확인할 수 있다.
12. 활동 멤버로서, 방이 최종 확정되면 `readOnly`가 참으로 표시되길 원한다. 그래야 프론트엔드가 편집 기능을 숨길 수 있다.
13. 활동 멤버로서, 현재 활동 중인 멤버의 이름과 합류 시각을 확인하고 싶다. 그래야 누가 방에 참여 중인지 알 수 있다.
14. 활동 멤버로서, 각 멤버의 설문 제출 여부를 확인하고 싶다. 그래야 방 전체의 설문 진행 상황을 알 수 있다.
15. 활동 멤버로서, 상세 멤버 목록이 합류 시각과 멤버 ID 순으로 정렬되길 원한다. 그래야 멤버 순서가 일관된다.
16. 방을 나간 사용자로서, 해당 방의 상세 조회가 거부되길 원한다. 그래야 활동 멤버만 방 정보를 볼 수 있다.
17. 방에 속하지 않은 사용자로서, 다른 사람의 방 상세를 볼 수 없기를 원한다. 그래야 방 정보가 멤버에게만 공개된다.
18. 존재하지 않는 방을 조회한 사용자로서, 방이 없다는 오류를 받고 싶다. 그래야 잘못된 방 ID를 구분할 수 있다.
19. 로그인하지 않은 사용자로서, 방 목록과 상세 조회가 모두 거부되길 원한다. 그래야 방 정보가 인증된 사용자에게만 제공된다.
20. 방 멤버로서, 목록이나 상세를 열기만 했을 때 마지막 확인 시각이 자동 변경되지 않기를 원한다. 그래야 명시된 `seenUntil` 기준의 확인 기록을 유지할 수 있다.
21. 여행 멤버로서, 방 수가 여러 개여도 각 방마다 별도 집계 쿼리가 발생하지 않기를 원한다. 그래야 목록 조회가 N+1 쿼리로 느려지지 않는다.
22. 활동 멤버로서, 상세 화면의 멤버 수가 많아도 멤버별 설문 상태를 하나씩 조회하지 않기를 원한다. 그래야 상세 조회에서 N+1 쿼리가 발생하지 않는다.

## Implementation Decisions

- 방 도메인의 기존 컨트롤러·서비스·Repository·DTO 구조와 `ApiResponse` 응답 형식을 사용한다. DTO에서 기존 `RoomStatus`를 재사용한다.
- `GET /api/rooms`는 HTTP 200과 본문 코드 `ROOMS_FETCHED`를 반환하고 `message`는 생략한다. `data`는 `RoomListResponse`이며 그 안에 `rooms` 목록을 둔다.
- 목록 항목에는 `roomId`, `name`, `destination`, `startDate`, `endDate`, `status`, `memberCount`, `opinionDeadlineAt`, `mySurveySubmitted`를 포함한다. 선택 사항인 `unvotedAgendaCount`는 포함하지 않는다.
- 목록은 페이지네이션하지 않는다. 현재 사용자의 활동 멤버십이 있는 모든 방을 포함하고, 방의 상태나 여행 날짜가 지났는지로 제외하지 않는다. 탈퇴한 방은 제외한다.
- `memberCount`는 방의 활동 멤버 수다. `mySurveySubmitted`는 현재 사용자의 해당 방 멤버에 연결된 SurveyResponse의 `submittedAt`이 존재하는지를 나타낸다.
- 전체 목록과 멤버 수 및 설문 제출 여부는 한 번의 집계 조회로 반환한다. 방별로 별도 쿼리를 실행하지 않는다.
- 목록 정렬은 `startDate` 오름차순, 동률이면 `roomId` 오름차순이다.
- `GET /api/rooms/{roomId}`는 HTTP 200과 본문 코드 `ROOM_FETCHED`를 반환하고 `message`는 생략한다.
- 상세 응답은 방 기본 정보, `readOnly`, `opinionDeadlineAt`, `surveyClosedAt`, `finalizedAt`, 활동 멤버 목록을 포함한다. nullable인 `surveyClosedAt`, `finalizedAt`은 값이 없으면 `null`이다.
- `readOnly`는 `RoomStatus.FINALIZED`일 때만 참이다.
- 상세 응답의 멤버 항목은 `memberId`, 사용자 이름, `joinedAt`, `surveySubmitted`를 포함한다. `memberId`는 User ID가 아닌 RoomMember ID다. `surveySubmitted`는 해당 멤버의 SurveyResponse `submittedAt` 존재 여부다.
- 상세 멤버 목록은 활동 멤버만 포함하고 `joinedAt` 오름차순, 동률이면 `memberId` 오름차순으로 정렬한다.
- 상세 첫 조회에서 방 존재 여부와 요청자의 활동 멤버 여부를 함께 확인한다. 두 번째 조회에서 활동 멤버와 설문 제출 여부를 일괄로 가져온다. 전체 조회는 두 번의 DB 조회이며 멤버별 N+1은 사용하지 않는다.
- 방 API는 로그인 사용자를 필요로 한다. R-03에서 방이 없으면 HTTP 404 `ROOM_NOT_FOUND`, 방이 있으나 요청자가 활동 멤버가 아니면 HTTP 403 공통 코드 `FORBIDDEN`을 반환한다.
- R-02와 R-03의 GET 조회는 `last_seen_at`을 갱신하지 않는다. 확인 시각 갱신은 H-03 `POST /api/rooms/{roomId}/seen`에서 전달된 `seenUntil`을 기준으로 한다.
- DB 스키마 변경은 필요하지 않다.

## Testing Decisions

- 좋은 테스트는 서비스나 Repository의 내부 호출 순서가 아니라 실제 HTTP에서 관찰되는 상태 코드와 응답, 인증 및 접근 권한, 조회된 멤버와 집계 결과를 확인한다.
- `RoomReadApiIntegrationTest` 하나를 인증 포함 HTTP 통합 경계로 사용하고, 기존 `IntegrationTest`와 Testcontainers MySQL을 재사용한다.
- 목록 테스트는 여러 방, 활동·탈퇴 멤버, 설문 제출 상태를 준비하고 로그인 사용자의 결과만 반환되는지, 방 상태·여행 날짜에 따른 제외가 없는지, 활동 멤버 수·설문 여부·정렬·빈 목록을 확인한다.
- 상세 테스트는 방 필드, `readOnly`, 활동 멤버만 포함되는지, 멤버 순서와 각 설문 제출 상태를 확인한다.
- 인증되지 않은 요청, 활동 멤버가 아닌 사용자 요청, 존재하지 않는 방 요청의 HTTP 상태와 응답 코드를 확인한다.
- 목록의 단일 집계 쿼리 요구는 SQL 횟수 assertion을 두지 않고 Repository 조회 설계와 리뷰에서 확인한다. 테스트는 외부 계약에 집중한다.
- 테스트 선례는 인증과 실제 HTTP를 확인하는 `AuthIntegrationTest`, 방 생성 요청을 검증하는 `RoomCreateIntegrationTest`다.

## Out of Scope

- 방 생성 및 수정, 초대 코드 참가, 탈퇴와 재합류
- 목록 페이지네이션, 검색, 필터, `unvotedAgendaCount`
- 설문 제출 또는 투표 상태 변경
- 조회에 따른 `last_seen_at` 갱신 및 H-03 API
- 타임라인, 비접속 요약, SSE 재연결 및 변경 기록
- 프론트엔드 화면과 편집 버튼 처리
- 데이터베이스 스키마 및 Flyway 마이그레이션 변경

## Further Notes

- 기존 용어집의 “활동 멤버”와 “내 방” 정의를 따른다.
- 목록 DTO 구조는 `RoomListResponse(List<RoomSummaryResponse> rooms)`다.
- 실제 문서 계약에서 `PlanRoomStatus`가 아니라 기존 `RoomStatus`를 사용한다.
- 구현은 R-02와 R-03 조회 API만 포함하며 방 생성 API는 기존 별도 티켓 범위다.
