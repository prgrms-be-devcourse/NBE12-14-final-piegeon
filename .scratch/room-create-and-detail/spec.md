# 여행방 생성 및 상세 조회 API

## Problem Statement

사용자는 여행방을 만들고 함께 여행을 조율할 멤버를 초대할 수 있어야 한다. 현재 방 엔티티와 방 멤버, 일차별 일정 모델은 있지만 이를 묶어 생성하고 방 정보를 안전하게 조회하는 API가 없다. 프론트엔드는 방 생성 후 방 정보, 멤버 목록, 편집 가능 여부와 설문 제출 여부를 확인할 수 없다.

## Solution

인증된 사용자가 여행 날짜와 방 정보를 보내면 여행방, 생성자 멤버, 여행 날짜별 일정이 하나의 트랜잭션에서 생성되는 API를 제공한다. 방 상세 API는 해당 방의 활동 중인 멤버에게 방 기본 정보와 활동 멤버 목록, 읽기 전용 상태, 설문 제출 상태를 반환한다.

## User Stories

1. 여행을 준비하는 사용자로서, 방 이름과 목적지 및 여행 날짜를 지정해 방을 만들고 싶다. 그래야 함께 계획을 시작할 수 있다.
2. 방을 만든 사용자로서, 생성과 동시에 해당 방의 멤버가 되고 싶다. 그래야 별도의 초대 수락 절차 없이 방을 이용할 수 있다.
3. 방을 만든 사용자로서, 생성 시 초대 코드를 받고 싶다. 그래야 다른 사람을 방에 초대할 수 있다.
4. 방을 만든 사용자로서, 초대 코드가 다른 방과 겹치지 않기를 원한다. 그래야 초대 코드로 올바른 방을 찾을 수 있다.
5. 여행 멤버로서, 여행 기간의 각 날짜에 대응하는 일정 공간이 미리 만들어지길 원한다. 그래야 날짜별 계획을 바로 작성할 수 있다.
6. 여행 멤버로서, 일정의 날짜 순서가 여행 시작일부터 차례로 배정되길 원한다. 그래야 일차와 실제 여행 날짜를 일관되게 이해할 수 있다.
7. 여행 멤버로서, 새 일정의 버전이 초기값으로 시작하길 원한다. 그래야 이후 일정 변경을 버전으로 추적할 수 있다.
8. 방을 만든 사용자로서, 설문 조율 마감 시각이 생성 시점부터 3일 뒤로 정해지길 원한다. 그래야 멤버가 의견을 제출할 기준 시각을 알 수 있다.
9. 방 생성 요청을 보내는 사용자로서, 이름과 목적지에 앞뒤 공백이 있어도 정리된 값으로 저장되길 원한다. 그래야 실수로 입력한 공백이 데이터에 남지 않는다.
10. 방 생성 요청을 보내는 사용자로서, 이름이나 목적지가 비어 있거나 50자를 초과하면 구체적인 입력 오류를 받고 싶다. 그래야 올바른 값으로 다시 요청할 수 있다.
11. 방 생성 요청을 보내는 사용자로서, 시작일의 자정이 현재 시각부터 24시간 이내이면 요청이 거부되길 원한다. 그래야 준비 시간이 충분하지 않은 여행방이 만들어지지 않는다.
12. 방 생성 요청을 보내는 사용자로서, 시작일이 오늘부터 1년 이상 뒤라면 요청이 거부되길 원한다. 그래야 지나치게 먼 날짜의 여행 계획이 만들어지지 않는다.
13. 방 생성 요청을 보내는 사용자로서, 종료일이 시작일보다 빠르면 `INVALID_DATE_RANGE` 오류를 받고 싶다. 그래야 잘못된 여행 기간을 바로 고칠 수 있다.
14. 방 생성 요청을 보내는 사용자로서, 시작일과 종료일을 포함한 여행 기간이 31일까지 허용되길 원한다. 그래야 최대 31일 여행을 날짜별 일정으로 계획할 수 있다.
15. 방 생성 요청을 보내는 사용자로서, 시작일과 종료일이 같은 당일 여행도 만들고 싶다. 그래야 하루 일정도 방에서 함께 조율할 수 있다.
16. 방 생성 요청을 보내는 사용자로서, 여행 기간이 31일을 초과하면 거부되길 원한다. 그래야 생성 과정에서 일정 데이터가 비정상적으로 늘어나지 않는다.
17. 방 생성이 중간에 실패한 사용자로서, 방이나 멤버 또는 일부 날짜만 생성된 상태가 남지 않기를 원한다. 그래야 실패한 생성 요청을 안전하게 다시 시도할 수 있다.
18. 방을 만든 사용자로서, 생성 응답에서 상세 조회와 같은 방 데이터 형식을 받고 싶다. 그래야 생성 직후 별도 조회 없이 방 화면을 표시할 수 있다.
19. 활동 중인 방 멤버로서, 방 기본 정보와 초대 코드를 다시 조회하고 싶다. 그래야 방의 계획 정보를 확인하고 다른 멤버를 안내할 수 있다.
20. 활동 중인 방 멤버로서, 방에 현재 활동 중인 멤버들의 이름과 합류 시각을 보고 싶다. 그래야 누가 방에 참여 중인지 알 수 있다.
21. 활동 중인 방 멤버로서, 방이 최종 확정된 경우 `readOnly` 상태를 받고 싶다. 그래야 프론트엔드가 편집 버튼을 숨길 수 있다.
22. 활동 중인 방 멤버로서, 각 멤버의 설문 제출 여부를 확인하고 싶다. 그래야 설문 진행 상황을 알 수 있다.
23. 활동 중인 방 멤버로서, 설문 응답이 아직 없는 멤버는 미제출로 표시되길 원한다. 그래야 제출 상태가 모호하지 않다.
24. 활동 중인 방 멤버로서, 설문 응답이 있는 멤버는 제출로 표시되길 원한다. 그래야 제출 상태를 별도 API 호출 없이 확인할 수 있다.
25. 방을 나간 사용자로서, 더 이상 방 상세 정보를 조회할 수 없기를 원한다. 그래야 활동 멤버만 방 정보를 볼 수 있다.
26. 방에 속하지 않은 사용자로서, 다른 사람의 방 정보를 조회하지 못하기를 원한다. 그래야 방 정보가 멤버에게만 공개된다.
27. 사용자가 없는 방을 조회한 경우, 존재하지 않는 방이라는 오류를 받고 싶다. 그래야 잘못된 방 ID를 구분해 처리할 수 있다.
28. 방 생성 요청을 보내는 사용자로서, 성공 시 HTTP 201과 `ROOM_CREATED` 응답 코드를 받고 싶다. 그래야 생성 결과를 명확히 처리할 수 있다.
29. 방 상세를 조회하는 사용자로서, 성공 시 HTTP 200과 `ROOM_FETCHED` 응답 코드를 받고 싶다. 그래야 상세 조회 결과를 명확히 처리할 수 있다.

## Implementation Decisions

- 기존 Spring Boot 도메인 구조를 따라 방 API의 컨트롤러, 서비스, 요청·응답 DTO, 방 도메인 오류 코드를 추가한다.
- 컨트롤러는 인증 사용자에서 사용자 ID를 얻어 서비스에 전달한다. 서비스는 다른 도메인의 Repository를 직접 사용하지 않고 해당 도메인의 서비스 경계를 이용한다.
- 현재 시각은 주입된 `Clock`으로 계산하며, 프로젝트의 Asia/Seoul 기준을 따른다.
- 방 생성 요청의 이름과 목적지는 앞뒤 공백을 제거한 뒤 각각 1~50자여야 한다.
- 날짜 검증은 다음 규칙을 따른다.
  - 시작일 자정이 현재 시각부터 24시간 이내이거나 이미 지난 경우 `400 DEPARTURE_TOO_SOON`을 반환한다. 경계 시각도 거부한다.
  - 시작일이 오늘부터 1년 이상 뒤인 경우 `400 DEPARTURE_TOO_FAR`를 반환한다.
  - 종료일이 시작일보다 빠르거나 시작일과 종료일을 포함한 여행 기간이 31일을 초과하면 `400 INVALID_DATE_RANGE`를 반환한다.
  - 시작일과 종료일을 포함해 최대 31일을 허용한다.
  - 같은 날짜의 시작일과 종료일은 1일 여행으로 허용한다.
- 초대 코드는 무작위 UUID 문자열의 첫 8자를 사용해 소문자로 저장한다. 초대 코드 조회는 대소문자를 정규화한다. 데이터베이스 UNIQUE 충돌이 발생하면 해당 생성 시도를 롤백하고 새 코드로 전체 트랜잭션을 재시도한다.
- 생성 과정은 단일 논리 작업으로 처리한다. `plan_room`을 `SURVEYING` 상태로 생성하고, 의견 마감 시각은 현재 시각 +3일로 계산한다. 이어서 요청 사용자를 멤버로 등록하고, 여행 일수만큼 `schedule_day`를 생성한다.
- 생성자 멤버의 최초 `joinedAt`과 `lastSeenAt`은 같은 현재 시각을 사용한다. 생성 시 설문 응답은 만들지 않는다.
- `schedule_day`는 여행 시작일을 1일차로 하여 `dayIndex=1`부터 연속 생성하고 각 행의 `version`은 0으로 시작한다.
- 생성 API는 `POST /api/rooms`이며 요청의 필드는 `name`, `destination`, `startDate`, `endDate`다.
- 생성 성공은 HTTP 201, 본문 코드 `ROOM_CREATED`, 메시지 `여행방을 만들었습니다.`를 사용한다. 응답 데이터는 상세 응답과 같은 구조를 사용한다.
- 상세 API는 `GET /api/rooms/{roomId}`이며, 방의 활동 멤버만 조회할 수 있다.
- 상세 응답은 방 ID, 이름, 목적지, 시작일, 종료일, 초대 코드, `RoomStatus`, 의견 마감 시각, 설문 종료 시각, 최종 확정 시각 및 멤버 목록을 포함한다.
- 상세 응답에는 `readOnly`를 포함하며 방 상태가 `FINALIZED`일 때만 `true`다.
- 멤버 항목에는 멤버 ID, 사용자 이름, 합류 시각, `surveySubmitted`를 포함한다. 설문 응답이 존재하면 `true`, 없으면 `false`다.
- 상세 응답 멤버 목록에는 `leftAt`이 null인 활동 멤버만 포함한다. 비활동 멤버 또는 방에 속하지 않은 사용자는 `403 FORBIDDEN`, 존재하지 않는 방은 `404 ROOM_NOT_FOUND`로 처리한다.
- 상세 조회 성공은 HTTP 200, 본문 코드 `ROOM_FETCHED`를 사용한다.
- 기존 테이블과 엔티티를 사용하므로 이 기능만을 위한 스키마 변경이나 Flyway 마이그레이션은 추가하지 않는다.
- API는 프로젝트 공통 `ApiResponse` 형식으로 응답하고 엔티티를 직접 반환하지 않는다.

## Testing Decisions

- 좋은 테스트는 구현 클래스의 내부 호출 순서보다 HTTP에서 관찰되는 상태 코드, 응답 본문, 방 생성의 원자성, 조회 권한과 DB에 저장된 결과를 검증한다.
- 기능 흐름은 가장 높은 테스트 경계인 인증 포함 HTTP 통합 테스트를 중심으로 검증한다. 테스트는 기존 `IntegrationTest`와 Testcontainers MySQL 기반을 사용한다.
- 날짜 업무 규칙은 프로젝트 테스트 규칙에 따라 Spring 없이 `RoomService`의 public 동작을 단위 테스트하고, HTTP 통합 테스트로 외부 응답 코드도 함께 검증한다.
- 생성 성공 테스트는 방, 생성자 멤버, 초대 코드, 마감 시각, 날짜별 `ScheduleDay` 개수·인덱스·초기 버전을 외부 응답 및 DB 상태로 확인한다.
- 생성 검증 테스트는 이름·목적지 길이, 24시간 이내 출발, 1년 이상 뒤 출발, 날짜 역전, 31일 초과를 요청으로 검증하고 실패 시 방·멤버·일정이 저장되지 않았음을 확인한다.
- 같은 날짜 여행 및 31일 여행의 성공 경계를 확인한다.
- 상세 조회 테스트는 활동 멤버와 비활동 멤버 접근, 존재하지 않는 방, 활동 멤버만 포함되는지, `readOnly` 상태, 각 멤버의 설문 제출 여부를 검증한다.
- 테스트 작성 방식은 실제 인증과 HTTP 요청을 검증하는 `AuthIntegrationTest`, 그리고 DB 통합 테스트의 `IntegrationTest` 및 Testcontainers 사용 방식을 따른다.

## Out of Scope

- 초대 코드를 통한 방 참가 API
- 방 탈퇴, 재합류, 멤버 관리 및 방장 역할
- 설문 제출 API 및 설문 업무 규칙 변경
- 일정 편집, 일정 항목 생성 및 버전 변경
- 방 상태 전이, 설문 종료, 최종 확정 처리
- 방 활동 내역, 비접속 요약, SSE 이벤트 발행
- Service 외부 API, Controller, DTO 외의 프론트엔드 기능
- 기존 스키마와 Flyway 마이그레이션 변경

## Further Notes

- 기본 triage 라벨 `ready-for-agent`로 기록한다.
- 방 생성 응답의 멤버는 방을 만든 사용자 한 명이며, `surveySubmitted`는 `false`, `readOnly`는 `false`다.
- 기간 상한 초과 오류 코드는 별도 명세가 없으므로 기존 날짜 범위 오류인 `INVALID_DATE_RANGE`를 사용한다.
- UUID 앞 8자의 충돌 가능성은 낮지만 8자리로 제한된 초대 코드 공간이므로 UNIQUE 제약과 재시도는 필수다.
- 기존 용어집과 방 활동 내역 ADR에 정의된 개념과 충돌하는 결정은 없다.
