# 방 활동 내역 공통 기록 명세

## 문제

여행방의 상태 변경은 멤버, 설문, 안건, 장소 후보, 일정 등 여러 도메인에서 발생한다. 각 도메인이 별도 방식으로 변경을 기록하면 방 타임라인, 비접속 요약, SSE 재연결 결과가 서로 달라지고, 트랜잭션 실패나 동시 변경에서 기록 누락·순서 역전이 생길 수 있다.

## 해결

모든 도메인이 동일한 방 활동 내역 기록 구조와 기록 서비스를 사용한다. 상태 변경과 기록은 같은 트랜잭션으로 저장하고, 업무 행위 하나당 항목 하나를 남긴다. 방 활동 내역은 방 타임라인·비접속 요약·SSE 재연결의 공통 데이터 원천이 된다.

## 사용자 스토리

1. 방 멤버로서, 방에서 일어난 주요 업무 행위를 시간순으로 볼 수 있어 다른 멤버의 진행 상황을 파악하고 싶다.
2. 방 멤버로서, 각 활동 항목에서 대상 종류와 대상 ID를 확인해 어떤 항목이 바뀌었는지 알고 싶다.
3. 방 멤버로서, 활동 항목에 생성·수정·삭제·확정 중 어떤 행위가 발생했는지 확인하고 싶다.
4. 방 멤버로서, 활동 당시의 요약 문구를 읽어 대상이 나중에 삭제되어도 당시 변경 내용을 이해하고 싶다.
5. 방 멤버로서, 멤버가 일으킨 활동에는 그 멤버의 현재 이름이 표시되고, 자동 처리에는 시스템이 표시되기를 원한다.
6. 방 멤버로서, 설문 마감, 조율 완료, 안건 결정, 장소 단계 변경, 일정 변경, 최종 확정처럼 방 계획에 중요한 행위만 타임라인에 보고 싶다.
7. 방 멤버로서, 표·동의 하나하나와 코멘트처럼 자주 발생하는 변경은 타임라인에 쌓이지 않기를 원한다.
8. 방 멤버로서, 장소 후보의 동의 수가 바뀔 때마다 기록을 받는 대신 후보의 단계가 실제로 바뀐 경우에만 활동 항목을 보고 싶다.
9. 방 멤버로서, 하나의 사용자 업무가 여러 데이터를 변경해도 이를 여러 내부 변경으로 쪼개지 않은 한 건의 활동으로 보고 싶다.
10. 방 멤버로서, 시스템이 설문을 마감하거나 자동 처리를 수행해도 해당 행위가 시스템 활동으로 남기를 원한다.
11. 방 멤버로서, 새 활동이 저장되는 도중 원래 상태 변경이 실패하면 그 활동이 타임라인이나 재연결에 나타나지 않기를 원한다.
12. 방 멤버로서, 동시에 발생한 같은 방의 활동도 로그 ID와 커밋 순서가 일치해 재연결 중 활동을 놓치지 않기를 원한다.
13. 방 멤버로서, 타임라인을 최신 항목부터 페이지 단위로 읽고 다음 페이지에서 중복이나 누락 없이 이전 항목을 이어서 보고 싶다.
14. 방 멤버로서, 방 활동 내역은 해당 방의 활동 중인 멤버만 읽을 수 있기를 원한다.
15. 방 멤버로서, 방을 나간 뒤에는 해당 방의 활동 내역과 비접속 요약을 더 이상 읽을 수 없기를 원한다.
16. 방 멤버로서, 마지막으로 방을 확인한 뒤 다른 멤버나 시스템이 만든 활동을 비접속 요약으로 확인하고 싶다.
17. 방 멤버로서, 내가 직접 만든 변경은 비접속 요약에서 제외되어 다른 멤버의 변경에 집중하고 싶다.
18. 방 멤버로서, 같은 종류의 비접속 변경을 묶어서 보고 그룹마다 최대 다섯 줄의 간결한 요약을 받고 싶다.
19. 방 멤버로서, 일정 보드 변경은 개별 항목 나열 대신 날짜별 변경 건수로 요약해서 보고 싶다.
20. 방 멤버로서, 비접속 동안 새로 등록됐다가 삭제된 장소는 새 장소 요약에 포함되지 않기를 원한다.
21. 방 멤버로서, 비접속 요약에서 미제출 설문과 내가 투표하지 않은 안건을 확인해 해야 할 일을 파악하고 싶다.
22. 방 멤버로서, 요약을 조회한 시점 이후에 발생한 변경을 놓치지 않도록 요약 조회 자체가 마지막 확인 시각을 앞당기지 않기를 원한다.
23. 방 멤버로서, 요약을 확인한 뒤 클라이언트가 전달한 `seenUntil`까지를 확인한 것으로 기록하고, 그 시각보다 오래된 값으로 확인 시각이 되돌아가지 않기를 원한다.
24. 방 멤버로서, 브라우저 연결이 끊겼다가 돌아오면 마지막으로 받은 로그 ID 뒤의 영속 활동을 순서대로 다시 받고 싶다.
25. 방 멤버로서, 재연결 시 표 수·코멘트처럼 로그 ID가 없는 일시적 이벤트가 재전송되지 않으면 해당 화면을 다시 조회할 수 있기를 원한다.
26. 방 멤버로서, 마지막 수신 ID 뒤에 놓친 영속 기록이 200건을 넘으면 일부 기록만 받는 대신 재동기화 안내를 받고 필요한 화면을 다시 조회하고 싶다.
27. 방 멤버로서, 실시간 활동은 상태 변경과 로그 저장이 커밋된 뒤에만 전달받아 롤백된 변경을 보지 않기를 원한다.
28. 도메인 개발자로서, 표준 기록 서비스를 호출해 방·행위자·대상·이벤트 종류·행위 상태·요약을 같은 방식으로 남기고 싶다.
29. 도메인 개발자로서, 장소 후보나 일정 블록이 삭제되어도 기록을 보존하고, 대상 행을 직접 참조하지 않고 당시 요약을 읽을 수 있기를 원한다.
30. 도메인 개발자로서, 방이 영구 삭제되면 해당 방이 소유한 활동 기록도 함께 정리되기를 원한다.

## 구현 결정

- 방 활동 내역의 표준 용어는 “방 활동 내역”이며, 화면이나 API의 “변경 이력”은 같은 개념을 가리킨다. 감사 로그나 전체 이벤트 소싱 저장소로 취급하지 않는다.
- 기존 도메인 구조에 맞춰 별도 `changelog` 도메인을 둔다. 공통 기록 저장 경계는 `ChangeLogService.record` 하나로 한다.
- 각 업무 도메인은 발생 시점에 맞는 요약 문구를 만들고, 방 ID, 선택적 행위자 멤버 ID, 대상 종류와 ID, 이벤트 종류, 행위 상태, 요약 문구를 공통 서비스에 전달한다.
- 공통 서비스는 호출자의 트랜잭션을 필수로 요구한다. 상태 변경과 로그 저장은 하나의 트랜잭션에 포함한다.
- 같은 방의 영속 기록 트랜잭션은 방 행 잠금으로 직렬화한다. 로그 ID는 해당 방의 SSE 재연결 커서로 사용한다.
- `change_log`는 추가 전용 테이블이다. 방 FK는 필수이며 방 삭제 시 기록을 함께 삭제한다. 행위자인 `plan_room_member_id`는 시스템 행위를 위해 NULL을 허용한다. 대상 엔티티는 여러 도메인에 걸치므로 `entity_type`과 `entity_id`로 표현하고 대상 FK는 두지 않는다.
- 각 행에는 `entity_type`, `entity_id`, `event_kind`, `action_status`, `summary`, 방·행위자 참조와 기존 Auditing 시각을 둔다. 요약 문구는 기록 당시의 문구로 저장하며 NULL을 허용하지 않고 길이를 임의로 제한하지 않는다.
- `entity_type`은 `MEMBER`, `PLAN_ROOM`, `AGENDA`, `PLACE_CANDIDATE`, `SCHEDULE_ITEM`을 사용한다. `action_status`는 `CREATE`, `UPDATE`, `DELETE`, `CONFIRM`을 사용한다. Enum은 이름을 문자열로 저장한다.
- `event_kind`는 비접속 요약 분류와 일치시킨다: `MEMBER_JOINED`, `MEMBER_LEFT`, `SURVEY_CLOSED`, `COORDINATION_COMPLETED`, `AGENDA_OPENED`, `AGENDA_RESOLVED`, `AGENDA_EXPIRED`, `PLACE_REGISTERED`, `PLACE_DELETED`, `PLACE_STAGE_CHANGED`, `PLACE_CONFIRMED`, `SCHEDULE_CHANGED`, `PLAN_FINALIZED`.
- 사용자가 이름을 변경할 수 없는 현재 기획에서는 요약 문구가 당시 이름을 포함해도 행위자 표시는 현재 사용자 이름을 사용한다. 이름 변경 기능이 추가될 때 과거 요약 문구의 이름 표시 방식을 다시 설계한다.
- 기록 대상은 첨부 명세의 업무 변경 표를 따른다. 멤버 합류·나감, 설문 마감, 조율 완료, 안건 열림·결정·만료, 장소 등록·삭제·단계 변경·확정, 일정 변경, 최종 확정을 기록한다. 개별 표·동의와 코멘트는 기록하지 않고, 장소는 단계가 바뀔 때만 기록한다.
- `change_log.id` 인덱스는 `(plan_room_id, id)`로 두어 방 범위의 커서 조회를 지원한다. 비접속 요약은 방과 생성 시각 인덱스를 이용한다.
- 타임라인은 방의 기록을 ID 내림차순으로 조회하고, `cursor`보다 작은 ID를 다음 페이지로 읽는다. 페이지 크기는 1~100, 기본값은 20이며 다음 커서가 없으면 `null`이다.
- 비접속 요약은 마지막 확인 시각 이후 다른 멤버와 시스템이 만든 기록을 사용한다. 확인 시각이 없으면 합류 시각을 기준으로 한다. 그룹별 최대 다섯 줄을 보여주고, 일정 변경은 날짜별 건수로 묶는다. 새 장소 요약에는 현재도 남아 있는 장소 후보만 포함한다.
- `POST /api/rooms/{roomId}/seen`은 `last_seen_at = max(현재 값, seenUntil)`로 갱신한다. 서버의 현재 시각으로 덮어쓰지 않는다.
- SSE에서 ID가 있는 이벤트는 로그 ID를 사용한다. 재연결 시 해당 ID보다 큰 방 기록을 오름차순으로 보낸다. 표 수, 코멘트, 재동기화 안내 등 ID가 없는 일시적 이벤트는 로그에 저장하거나 재연결 때 재전송하지 않는다.
- 재연결 누락 기록이 200건을 초과하면 일부만 재생하지 않고 ID가 없는 `resync.required` 제어 이벤트를 보낸다. 클라이언트는 기존 연결을 닫고 R-03, B-01, P-03, V-01을 다시 조회한 뒤 새 연결을 연다. 실시간 발행은 커밋 뒤에 수행한다.
- SSE 타임라인은 방 화면마다 방 단위 연결 하나를 사용한다. 서버는 구독을 등록한 뒤 현재 마지막 활동 ID를 기준점으로 `connected` 준비 이벤트(`latestEventId`)를 보낸다. 클라이언트는 준비 이벤트 후 일반 최신순 커서 페이지를 조회하고, 조회가 끝날 때까지 수신한 이벤트를 버퍼링한 뒤 활동 ID로 중복 제거해 합친다. 타임라인 API에는 초기 기준 ID 상한 파라미터를 두지 않는다.
- 타임라인은 최신순으로 표시한다. 최신 항목을 보고 있으면 새 활동을 맨 위에 추가하고, 이전 항목을 읽는 중이면 읽던 위치를 유지하면서 새 활동 표시를 제공한다. 이전 페이지는 현재 가장 오래된 활동 ID보다 작은 ID로 조회한다.
- 타임라인 항목은 대상 종류와 ID를 제공한다. 대상이 남아 있으면 해당 화면으로 이동하고, 삭제되었거나 이동할 수 없으면 기록만 표시한다.
- 읽음 처리는 화면에 실제 표시된 활동까지만 한다. 확인 API의 기존 계약대로 마지막으로 표시한 활동의 `createdAt`을 `LocalDateTime` `seenUntil`로 전달하고, 읽지 않은 활동은 확인 처리하지 않는다.
- 방 멤버가 나가면 활성 SSE 연결을 종료하고 이후 재접속을 거부한다. 활동 멤버 조회에서는 비멤버와 나간 멤버를 구분하지 않고 `FORBIDDEN`으로 응답한다. 개인 알림은 방 공통 활동과 별도 개념으로 둔다.
- SSE 연결은 15초 주기의 keep-alive에서 활동 멤버 자격을 다시 확인한다. 방을 나간 멤버의 스트림은 다음 확인에서 종료한다.
- 공통 발행·구독 계약은 단일 서버에서의 연결 관리를 대상으로 한다. 커밋 후 전송 직전 서버 종료로 빠진 실시간 전달은 재접속 재생으로 복구한다. 다중 서버 간 실시간 전파는 배포 요구가 생기면 별도 확장한다.
- 타임라인은 `GET /api/rooms/{roomId}/change-logs`에서 `cursor`, `size`로 조회한다. `cursor`보다 작은 ID를 내림차순으로 가져오며 페이지 크기는 기본 20, 범위 1~100이다. 응답의 각 항목은 `logId`, `actor`, `entityType`, `entityId`, `action`, `summary`, `createdAt`을 포함한다. `actor`는 `{memberId, name}`이고 시스템 행위는 `null`이다. 응답의 `nextCursor`가 `null`이면 마지막 페이지다. 성공 본문은 공통 `ApiResponse`로 감싼다.
- 타임라인 오류는 로그인 안 됨/세션 만료 시 `401 UNAUTHORIZED`, 잘못된 `roomId` 또는 `size` 시 `400 INVALID_INPUT`, 없는 방이면 `404 ROOM_NOT_FOUND`, 비멤버와 나간 멤버는 `403 FORBIDDEN`이다.
- SSE는 `GET /api/rooms/{roomId}/change-logs/stream`에서 연결한다. `connected` 이벤트는 구독 등록 후 기준 활동 ID를 `latestEventId`로 제공하고, 영속 기록은 `activity` 이벤트와 동일한 활동 ID를 SSE ID로 보낸다. `Last-Event-ID` 재생 한도를 넘으면 `resync.required`를 보낸다.
- 이번 구현은 공통 `changelog` 구조와 `room`, `room member`, `survey` 경계에 한정한다. 장소·안건·일정 도메인의 업무 경로와 기록 연결은 변경하지 않는다.
- 데이터베이스는 MySQL 8.4이며 기존 Auditing과 `BaseEntity`를 재사용한다. 방 활동 테이블은 V17에서 생성하며, 방 멤버 확인 시각의 NULL 허용은 V19에서 반영한다.
- 저장 구조 작업은 공통 기록 모델과 기록 서비스까지 구현되어 있다. 이번 후속 작업은 타임라인 조회, SSE 연결·발행·재연결, 확인 시각 API와 인증 포함 HTTP 통합 검증을 추가한다.

## 테스트 결정

- 내부 어노테이션이나 잠금 호출을 직접 검증하기보다, 클라이언트와 호출 도메인이 관찰하는 결과를 검증한다. 상태 변경과 기록의 원자성, 방별 활동의 순서, 행위자·시스템 표기, 대상 삭제 후 요약 보존, 방별 커서 조회를 확인한다.
- 기존 `@IntegrationTest`와 Testcontainers MySQL을 사용해 ChangeLog 기록 서비스와 저장소를 통합 경계에서 검증한다. Flyway와 Hibernate 검증을 통해 V17/V19 스키마·연관관계·인덱스가 실제 MySQL에서 적용되는지도 확인한다.
- 같은 방의 병렬 상태 변경으로 생성된 ID와 커밋 순서가 재연결에 안전한지 검증한다. 다른 방의 멤버를 행위자로 기록할 수 없고, 시스템 기록은 행위자 없이 저장되는지도 확인한다.
- 타임라인 커서 조회는 최신순 페이지와 이전 페이지의 연속성을 확인한다. 재연결 조회는 마지막 ID 이후 기록을 오름차순으로 반환하며 방이 섞이지 않는지 확인한다.
- 비접속 요약용 저장소 조회는 본인 변경을 제외하고 다른 멤버·시스템 변경을 포함하는지 확인한다. `/seen` API가 구현될 때는 `seenUntil`의 단조 증가와 요약 조회가 확인 시각을 바꾸지 않는 동작을 통합 테스트한다.
- `ChangeLogTimelineIntegrationTest` 하나의 인증 포함 HTTP 통합 경계에서 타임라인·SSE·재연결·확인 시각을 검증한다. 기존 테스트 선례는 방 조회 HTTP 통합 테스트와 `AuthIntegrationTest`다.

## 범위 밖

- 비접속 요약의 Controller, DTO, 전체 집계 비즈니스 로직.
- 장소·안건·일정 도메인의 활동 기록 연결과 업무 변경.
- 설문·안건·장소·일정·댓글 등 각 업무 기능 자체, 상태 전이, 투표·동의·코멘트 로직은 구현하지 않는다. 각 도메인의 기록 연결은 후속 작업에서 수행한다.
- 사용자 이름 변경 기능이나 이름 변경 뒤 과거 요약 문구를 갱신하는 동작을 구현하지 않는다.
- 감사 목적의 모든 DB 변경 추적이나 이벤트 소싱, 개별 투표·동의·댓글 이력은 구현하지 않는다.

## 추가 사항

- 저장소의 기존 ADR은 없었으며, 이 설계는 방 활동 내역을 공유하는 영속 기록으로 다룬다.
- 공통 모델과 기록 서비스는 이미 구현되어 있다. 이 구현은 허용한 도메인 경계 안에서 타임라인 조회, SSE 전달·재연결, 확인 시각 API를 추가한다.
